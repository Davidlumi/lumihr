# lumi — reward-persona UX/UI audit (pre-production polish), 2026-08-10

Method: 10 parallel reward-persona auditors over the frontend (web/js/*.js + web/css/app.css), each grounded in code, + a synthesis pass; plus a live authenticated walk (Overview + Pay grid). 72 raw findings -> the tiers below. Audience lens throughout: a time-poor UK reward/HR manager who is NOT a data analyst. Top findings were re-verified against the code before this was written.

## Cross-cutting themes

- ONE COLOUR, ONE MEANING is broken twice over. Mechanically: eight verdict-ink tokens are defined self-referentially so green/red/purple verdict text renders near-black (app.css). Semantically: the exact words 'above market' are painted RED on the position gauge, Signals tags, category ruler and board-pack donut, but GREEN on the metric pill, chart You-marker and the pack's exec-summary lead. The premium colour language a buyer is paying for is both degraded and self-contradicting. Fix the tokens, then pick ONE valence for below/on/above market product-wide and add a visible legend on every RAG surface.
- ANALYST NOTATION LEAKS TO A NON-ANALYST PERSONA. Percentiles with no gloss ('P62', 'typical metric', bare 'P73' in the matrix), 'n=42', 'cohort', 'asked as v1', '5+ suppression', '72% of 90%'. Each is invisible to the reward manager the product explicitly serves and violates the minimal-jargon editorial line. Needs one coordinated de-jargon pass, plus routing all <5-org suppression copy (currently worded six ways) through a single constant.
- MEANING IS HIDDEN IN HOVER-ONLY TOOLTIPS. The Confidence chip, refresh-flag reason, 'labour intensity', the percentile explainer and the 'off the norm != bad' framing all live only in native title= attributes — unreachable on touch, keyboard and screen readers, i.e. invisible on the tablet an HR user actually presents from. Surface the key meaning on-screen; reserve title= for secondary detail.
- RULED TERMINOLOGY SINGULARS ARE NOT ENFORCED. pulse vs survey, answer vs response, suggest vs request, 'To do' vs 'To answer', cohort vs group. David has ruled that consistency IS the credibility on a 10k product; right now the signature 'Pulse' feature calls itself a 'survey' on the same screen. One glossary-driven find-and-replace sweep.
- SAME CONCEPT, MANY VOICES AND LABELS. The profile step has four names, the pre-unlock empty state has three hero headlines, suppression has six wordings, the export verb is 'Download PDF' in three files and 'Print / save as PDF' in two, and back-navigation uses four different atoms. Centralise shared copy and UI atoms so one concept reads one way.
- THE FIRST-RUN ONBOARDING FUNNEL IS FRAGMENTED. Competing CTAs restating one promise, an ungated Share button that can leak an empty benchmark, no privacy/trust line at the moment of decision, and duplicate interstitials for a single step. Give the first screen one owned call-to-action and state the give-to-get + privacy story where the decision is made.
- ACCESSIBILITY BASELINE GAPS RECUR ON THE MOST-USED CONTROLS. Effectively-invisible keyboard focus rings on the data-entry forms, missing aria-current on the nav, missing aria-label on the destructive dashboard-toolbar buttons, a non-keyboard-operable chart click target, and meaning stranded in title=. One a11y pass clears most of them cheaply.
- CARD-TO-DETAIL PARITY. Colour and verdict for the same metric are computed from different inputs on the dashboard card vs the full metric page, so clicking through silently flips green->blue or 'ahead' -> 'in line'. Drive both surfaces from one source so a click-through never changes the answer.


## HIGH — fix before prod

### Verdict-ink colour tokens are self-referential and render near-black  _(S)_
- **Where:** Whole app — every pill/chip/verdict/lens/confidence label (web/css/app.css :root L122-144, ~30 consumers)
- **Why:** Eight ink tokens are defined as var(--x-ink) referencing themselves — invalid at computed-value time — so deep-green/red/purple verdict TEXT falls back to inherited near-black. The product's core 'one colour, one meaning' language is silently gone, and it breaks inconsistently within a single control (amber survives via inline mixes while green/red go black). Introduced by commit 19a2df3 (DS-4), whose message wrongly claims it was verified.
- **Fix:** Redefine each token with the recipe DS-4 was replacing: --favourable-ink: color-mix(in srgb, var(--favourable) 78%, var(--ink)); apply the same 78%-ink pattern to --unfavourable-ink, --neutral-perf-ink, --differs-ink and the four --lens-*-ink tokens.

### 'Above market' reads RED on some surfaces and GREEN on others, with no legend anywhere  _(M)_
- **Where:** Overview gauge/donut, Signals tags, category PercentileRuler, board-pack donut vs metric pill, chart You-marker, pack exec-summary lead
- **Why:** The fastest at-a-glance cue in the product inverts for identical wording: a reward manager sees a red 'above market' tag in Signals, clicks through, and the same metric shows a green 'Above market' pill and diamond; the board-pack donut colours the 'above median' lead red while the headline sells it as the good news. Two colour codes for three words, no on-screen key on either — this is the classic thing that makes people stop trusting a dashboard.
- **Fix:** Decide one colour model for below/on/above market product-wide (position-lens 'on-market is target' vs favourability 'higher is better' are different questions — do not leave them to collide). Then add a one-line key to each RAG surface labelling the lens ('vs the market' / 'vs your aim'), and reconcile the board-pack donut with its own exec-summary framing.

### The Pulse feature calls itself a 'survey' and counts 'responses' not 'answers'  _(M)_
- **Where:** web/js/pulses.js — RunPulsePage / PulseBuilder / PulseComposer / PulseLaunchPanel / PulsesPage
- **Why:** 'Pulse' is the product's signature concept and a ruled singular, yet the same screen titled 'Run a pulse' with a 'New pulse' button then says 'No surveys yet', 'Create your first survey', 'Survey name', '← Your surveys'. The persona genuinely can't tell whether a pulse and a survey are the same object. Counts say 'response(s)' where the core benchmark everywhere else says 'answers'. Admin side is already correct, so this reads as an unfinished bolt-on on a 10k product.
- **Fix:** Replace every member-facing 'survey' -> 'pulse' and 'response(s)' -> 'answer(s)' in pulses.js (No pulses yet / Create your first pulse / Pulse name / Discard this draft pulse? / ← Your pulses); keep 'survey' only in code comments. Also fix the list-card 'N participating' -> 'N organisation(s)' with plural guards.

### Regenerating a stale board pack orphans already-sent share links on the OLD numbers  _(M)_
- **Where:** web/js/commercial.js BoardPackView — makeShare L164, regenerate ~L228-236, stale banner L244-247
- **Why:** The board pack is the flagship deliverable. The stale banner tells the manager to 'Regenerate for current numbers'; they do, reasonably believing the board now sees current figures — but regenerate mints a new pack_id and nav()s to it, while the link they emailed still serves the old stored payload. A board presenting superseded reward data unknowingly is a serious credibility failure.
- **Fix:** Make Regenerate update-in-place (reuse pack_id so live links follow). If a new pack is intended, warn on regenerate and in the stale banner: 'Existing share links still point to the previous version — re-share to update recipients', and surface which live links exist.

### The first screen a new admin sees stacks three competing CTAs for one promise  _(M)_
- **Where:** First-run Overview — web/js/pages.js OverviewPage (WelcomeHero L137, pending arc CTA L895, locked Signals CTA ~L1517)
- **Why:** The most-seen first screen restates the unlock promise three ways (WelcomeHero, the pending arc 'Add your reward data', the locked Signals card 'Add your reward data') with three competing primary buttons — and the two lower ones skip past the profile/terms sequence the checklist above just laid out. A time-poor manager has no single obvious next step at the exact moment onboarding must be frictionless.
- **Fix:** While pre-terms/pre-unlock, suppress the CTA buttons on the pending arc and locked Signals card (keep the visuals) so WelcomeHero owns the one call to action; or collapse the first-run Overview to a single hero.

### On lower-is-better metrics the verdict word and arrow contradict the printed percentile  _(S)_
- **Where:** Per-metric position pill + numeric matrix — web/js/card.js cardPosition L399-412; app.js MetricPage L1598; charts.js L315
- **Why:** For attrition, absence, gap and cost metrics the pill shows a polarity-corrected verdict ('down-arrow Below market') next to the RAW percentile ('· P80'), so word/arrow point one way and the number the other — on exactly the metrics where direction matters most. The pill carries no 'lower is better' cue to resolve it, so the headline read looks self-contradictory and buggy.
- **Fix:** On lower-is-better metrics either print the polarity-corrected percentile (100-p) so word/number/arrow agree, or append the existing '· lower is better' cue to the pill and the matrix Position header, or drop the raw '· P' from the corrected pill and keep the number only in the neutral Exact-figures row.


## MED — strong polish

### Analyst notation and unexplained percentiles at the point of use  _(M)_
- **Where:** Overview arc marker (pages.js L392-413), di-pill L1356, MatrixHeat Position col (charts.js L315), sample labels 'n=42' (core.js L570), pulses 'asked as v1' L310 / '5+ suppression' L245
- **Why:** The persona is explicitly not a data analyst, yet the single most prominent number on the Overview is 'P62 · typical metric', the matrix prints bare 'P73' rows, peer counts read 'n=42', and the flagship pulse report exposes 'asked as v1' and '5+ suppression' — making a give-to-get report look like a debug view. Every one breaks the product's own 'no unexplained P / minimal jargon' rules.
- **Fix:** Coordinate one de-jargon pass: gloss or tooltip-link the P marker ('half your measures sit above the market mid-point'); give matrix Position cells word+number or a triangle glyph; render peer counts as plain '42 organisations' while the composition flag is off; delete 'asked as v{n}' from member UI and drop the '5+ suppression' header token (the footer already states it).

### 'Download PDF' opens the OS print dialog, and the export verb is named two ways  _(S)_
- **Where:** web/js/commercial.js L241, share.js L74, pulses.js L248 ('Download PDF') vs strategy.js L360 + sample-board-pack.html L97 ('Print / save as PDF')
- **Why:** A time-poor HR user clicks 'Download PDF' expecting a file in Downloads (as the neighbouring CSV button does); instead a print dialog appears and they must know to pick 'Save as PDF' — some send it to a physical printer or abandon. The product also contradicts itself on its core export verb, which reads as unfinished.
- **Fix:** Standardise on the honest label 'Print / save as PDF' everywhere (board pack, share viewer, pulse, strategy), or genuinely generate a PDF blob. Pick one string and apply it in all four files.

### Meaning is trapped in hover-only tooltips, invisible on touch/keyboard/SR  _(M)_
- **Where:** Confidence chip (pages.js L39-54), refresh flag (submission.js L429), 'labour intensity' (strategy.js L654), percentile explainer, practice-bucket neutral framing (pages.js L1041)
- **Why:** The reassurance an HR person needs — that Confidence 8/10 is sample size not accuracy, that a refresh is a routine yearly re-check, that 'off the norm' is rarity not a gap, what 'labour intensity' means — all live only in native title= attributes. On the tablet they present from, and for keyboard/screen-reader users, these read as bare jargon with no meaning available.
- **Fix:** Surface each key meaning as visible on-screen text (a caption or inline gloss); keep title= for secondary detail only. E.g. relabel the chip 'Sample 8/10' or show the driving n inline; add one caption line to the refresh flag and the labour-intensity note.

### Required 'Primary objective' says 'press 1, 2 or 3' but has FIVE options  _(S)_
- **Where:** web/js/strategy.js StrategyPage stagefoot L674 (caption) vs OBJECTIVES L58 (5 entries), keydown L602 accepts 1-5
- **Why:** This is a mandatory gate the persona cannot skip. Told to 'press 1, 2 or 3', a time-poor manager assumes only three of the five focus options are selectable, or thinks the screen is broken — right at a conversion-critical moment. 'Choose a position' is also the wrong noun for an objective.
- **Fix:** Make the digit range dynamic from the field's option count (3 for the market/mix scales, 5 for primary_objective), or drop the digit list for 'Choose one to continue'. Change 'Choose a position' to 'Choose your focus'.

### A brand-new org can mint a public link to an empty, locked benchmark  _(S)_
- **Where:** web/js/pages.js hero — ShareButton role-only check L296-304 vs ExportBoardPack unlock gate L236
- **Why:** ExportBoardPack correctly hides pre-unlock, but its identical-looking sibling ShareButton renders for any admin, so a new admin can create a read-only link and share an empty/locked benchmark with their board — embarrassing, and it looks unfinished that one hero action gates and the other doesn't.
- **Fix:** Gate ShareButton on contrib.insights_unlocked exactly as ExportBoardPack is (return null pre-unlock), or disable it with an explanatory tooltip until there is a position to share.

### Strategy Section 02 'Ahead of aim / Behind aim' is never explained and the dot colour isn't keyed  _(M)_
- **Where:** web/js/strategy.js aimRead L342-349, caption L391, legend L393, dot colours a-on/a-off L309-315
- **Why:** This is the centrepiece chart the brief says must be comprehensible. 'Ahead of aim' reads as good in plain English, but if you deliberately aim below market and land on market you're shown 'Ahead of aim' (overspending) against a neutral navy dot — everyday valence contradicts the colour. The caption only defines the band; nothing tells the persona what ahead/behind mean or why one dot is green and another navy, so they can't tell whether an off-aim row is a problem.
- **Fix:** Extend the caption to define all three reads ('above your aim / on aim / below your aim') and add the green dot to the legend as 'on aim'. Consider 'Above aim'/'Below aim' to kill the win/lose connotation.

### Same metric flips verdict and colour between the card and the full view  _(M)_
- **Where:** web/js/card.js BenchmarkCard (cfav L48/98, meaningPos L49/103) vs app.js MetricPage (pos.kind L1656, meaningLines L1726)
- **Why:** The card colours by SIGNAL (cardFav returns null unless exactly one flag), the metric page colours by POSITION. So an above-market metric that hasn't crossed a signal threshold shows a plain-blue diamond and 'broadly in line' on the card, then a GREEN diamond and 'ahead of most similar organisations' when opened — same metric, same peer group. The click-through silently changes the verdict, which reads as a bug.
- **Fix:** Drive both surfaces from one source — either colour the metric-page marker/narrative from cardFav too (matching the card's deliberate 'no flag = neutral' rule), or colour both from position; not one each.

### Two verdicts in two colour languages sit on one card with no shared key  _(M)_
- **Where:** web/js/pages.js 'Where you stand' — AlignmentChip L115-120 (navy) beside RAG donut/verdict L340-384
- **Why:** A manager sees amber 'Below market' next to navy 'On aim' (or red 'Above' next to 'On aim') and can't tell which is the answer or why they disagree. Nothing states that market colour = vs peers and navy = vs your own strategy. Two 'are we OK?' reads without a legend is exactly the ambiguity that erodes trust.

### Error empty-states are inconsistent — several show the raw error, one shows no body  _(S)_
- **Where:** Missing reassurance tail: pages.js L1983, app.js L654, commercial.js L31/764/880/1047/1350; pages.js L3272 (no body). Correct form: pages.js L98/2400/2626 etc.
- **Why:** On a bad fetch the persona sometimes sees a calm '… — nothing is lost.' and sometimes a bare 'Something went wrong' or a raw err.message, on surfaces holding their comp data. The inconsistent, occasionally raw tone reads as flaky and directly contradicts the editorial ruling that error states are unified.
- **Fix:** Route every EmptyState tone='error' body through one helper that appends the fixed reassurance line; never render bare err.message on member surfaces.

### 'Suggest a metric' is named four ways and built as two separate modals  _(M)_
- **Where:** web/js/commercial.js RequestMetricModal L1176 vs SuggestMetricModal L1229; triggers app.js:1365/1696/464, commercial.js:670
- **Why:** The canonical ruled term is 'Suggest a metric', but the persona meets 'Request a metric', 'Request this metric' and 'Suggest a related metric' depending on location, opening two visually different dialogs with different success copy for one identical outcome (both POST /api/metric-requests). It looks like two features and erodes the consistency that is the product's credibility signal.

### Refresh flags never say why or how often, and 're-save to confirm' doesn't clear them  _(S)_
- **Where:** web/js/submission.js flag L429-430 / copy L426; pages.js DomainDataView L3443, dh-stat L3340
- **Why:** The amber 'Refresh' flag and 'N to refresh' counts give no cadence or reason, so the manager can't judge urgency and either ignores the nudge or worries needlessly. Worse, the copy says 'update, or re-save to confirm', but the flag only clears on the next Submit (per the nRefresh comment) — so re-saving as instructed leaves the flag up, reading as a bug that erodes trust that their action registered.

Align the two refresh lines to one wording.

### One profile step carries four names and shows two intro screens before any data entry  _(M)_
- **Where:** web/js/app.js L688/995/1027; submission.js L39/42; route title '/profile'

### Board packs — the flagship output — is undiscoverable once you leave the Overview  _(S)_
- **Where:** web/js/app.js NAV_INDEX L1280-1296 (no /boardpack) though route + TITLES L53 exist; only entry is the Overview dropdown (pages.js L285)
- **Why:** Board reporting is the reward manager's core output, but the page has no rail item and no command-palette entry, so typing 'board pack' into the searchbox they're trained to reach for returns nothing, and there's no way to find a pack generated last week. A headline 10k feature feels hidden.
- **Fix:** Add a NAV_INDEX entry ({label:'Board packs', route:'/boardpack', group:'Pages', kw:'board report export pdf'}) so search finds it; ideally add a rail item under 'Your organisation' (file-text icon) too.

### Keyboard focus ring is effectively invisible on the data-entry forms  _(S)_
- **Where:** web/css/app.css L809/816/870/988/2315/2758 (outline:none + faint --blue-tint box-shadow) vs the --focus-outline token L169
- **Why:** The forms where the manager types pay/benefit data set outline:none on :focus and replace it with a ~1.1:1 box-shadow, overriding the documented 5.2:1 focus token — and because it's :focus (not :focus-visible) at class specificity it wins for mouse and keyboard alike. A keyboard user gets essentially no focus ring, and the same input has a strong ring on search but an invisible one on data entry, which reads as unfinished.
- **Fix:** Replace outline:none + the --blue-tint box-shadow on these :focus states with outline: var(--focus-outline) (keep the border-color change). If a ring is wanted, use --blue-bright at >=2px to clear the 3:1 non-text floor.

### Board-pack print layout silently clips unbudgeted prose and can drop the confidentiality footer  _(M)_
- **Where:** web/css/app.css @media print .pack-page height:296mm; overflow:hidden L2485-2487; commercial.js exec-summary/key-findings/opportunity prose (~L200-332) render with no fit budget
- **Why:** Only the evidence tables are length-budgeted (sliced to 8 with an honest remainder). The AI/deterministic narrative, key-findings list and opportunity prose are unbounded inside a fixed page with overflow:hidden, so a longer narrative can silently lose its last paragraph — potentially the PercentileRuler or the 'Private & confidential' footer — with no signal to the user. A pack that quietly drops content undermines trust in the whole document.
- **Fix:** Budget the prose the way tables are (cap length or measure-and-flow to a continuation page) or replace overflow:hidden with a page-break strategy so nothing is lost, and add a build/QA check that flags packs exceeding one sheet.
